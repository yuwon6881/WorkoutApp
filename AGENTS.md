# WorkoutApp guidance

Applies only to this independent repository; app-specific rules override the parent's FinancialApp rules. `CLAUDE.md` is canonical; keep `AGENTS.md` byte-identical. After editing, run `node scripts/sync-docs.mjs`, then verify with `node scripts/sync-docs.mjs --check`.

## Keep this guidance concise

- Update the implemented-feature index in the same change as a feature addition, removal, or material behavior change. Update an existing bullet before adding one; group capabilities and link to detail instead of keeping a changelog here.
- List implemented behavior only; plans are not shipped features. Keep this file near 100 lines or fewer. Product details belong in `README.md`, deployment instructions in `deploy/README.md`, and improvement work in `ENHANCEMENT_PLAN.md`.

## UI standardization

- Search `web/src/components/ui/`, nearby feature components, `web/src/lib/`, and `web/src/index.css` before adding UI. Reuse `Button`, `Modal`, `Select`, `MultiSelect`, `SegmentedControl` (two- or three-option choices), `Switch` (on/off preferences), `SettingRow`, `RpeControl`, `Skeleton`, `StartupScreen` (sign-in and full-page recovery), and shared motion components; extend existing patterns rather than making another button, dialog, card, or selector system.
- Feature actions use `Button`, including icon actions with explicit accessible names. Raw buttons and selects belong inside shared primitives; form controls and compact table rows must use `Select` rather than unstyled native popups to preserve the themed dark/light styling, keyboard navigation, and custom scrollbars. Scrollbars app-wide and inside dropdowns/modals must use thin semantic theme colors (`var(--border-hover)` thumb, transparent track). Card failures use `CardFeedback` with a compact tone icon, readable copy, and a trailing retry action; startup connection failures use `ConnectionRecovery`. Repeated field/error behavior should become one shared primitive using `web/src/lib/validation.ts`, not copied feature markup.
- Use the app's dark and light themes through the semantic variables in `web/src/index.css` (such as `--bg`, `--surface`, `--text`, `--muted`, `--accent`, `--on-accent`, `--red`, `--red-soft`, `--red-border`, and `--effort-max`/`-hard`/`-moderate`/`-easy` for the RIR scale). The themes match NutritionApp: dark is Midnight Lime (near-black canvas, hairline cards, lime accent with dark on-accent text) and light is Lavender (lavender canvas, white borderless cards with a soft violet shadow, violet accent); cards use `--card-border`/`--shadow` on a restrained radius scale (`--radius` 14px cards, `--radius-control` 10px buttons, fields, tabs and segmented tracks, `--radius-modal` 18px dialogs; only small chips, badges and circular icon actions are pills), phones use a floating glass dock with a raised round workout action, and wider windows use a side navigation (a 232px column with the same workout action and an account card, or a 96px icon rail from 640 to 1023px). Text on accent must use `var(--on-accent)`, not `var(--bg)`. ## Code standardization

- Inspect Git status and preserve concurrent edits. Run commands in this repository, keep commits separate from sibling apps, and do not commit/push/deploy unless requested.
- Keep components and minimal API endpoints thin. Move reusable coordination into focused hooks, pure calculations into `web/src/lib/`, and backend rules into `api/Services/`. Reuse DTOs, validation, training/unit helpers, and request/error handling.
- Prefer explicit types, clear names, small functions, and readable multiline formatting. Avoid `any`, compressed logic, dead code, swallowed failures, and premature abstractions. Comments explain why.
- Aim for <=300 lines per new source file; split before 500 along responsibility boundaries. Do not grow oversized services: extract the responsibility being changed. Generated migrations are exempt. Never compress code to satisfy the limit.
- Server behavior is authoritative. Preserve tenancy, revision checks, transactions, idempotency, timeouts/cancellation, and structured error handling. Add regression coverage before changing authentication, save ordering, progression, or program lifecycle. Never rewrite applied migrations.

## Data boundaries

- FitnessAccount alone stores credentials. `IdentitySubject` is immutable; display name is mutable metadata. Consumer apps exchange OIDC codes server-side and use local sessions; never add consumer password storage or registration.
- The server remains authoritative for training data. Account-scoped storage (IndexedDB on web/PWA and native SQLite in `noBackupFilesDir` on Android) may retain only the active workout recovery snapshot, unfinished set draft, and serializable pending edits/timing/rest/finish operations needed to continue that session, plus one account's last launch summary (account, preferences, active slot summary, next workout; no sessions, history, program days or import drafts; none while a workout is open; written by the same build within 14 days; removed at sign-out) shown only until the live launch read answers; all records stay partitioned by account, carry stable mutation identities, and reconcile through server revisions before replay. Do not cache training data in the service worker or retain completed history/program data locally. The device-local rest deadline is separately account/session scoped. Browser storage is best-effort, not a backup; static-shell caching must not cache API responses or return SPA HTML for API/asset failures.
- Kilograms are canonical and pounds are display conversion. Unknown load stays unknown and is excluded from volume; zero is a real bodyweight load. A rep target a program never states stays empty: it is never prefilled; a combined target shows available effort alone, or a dash when the whole target is empty. Freeze session bodyweight context so later weigh-ins do not rewrite historical calculations.
- Suggestions prefill but never pre-log sets or overwrite prescribed rep/RPE targets. Only completed sets enter history. Preserve effort, resistance-mode, phase-order, skip/completion, and draft-versus-finished semantics.
- The exercise catalog is global and seed-owned, read-only to users. Imports remain editable before program creation; preserve extracted/inferred/user-edited provenance and unresolved exercises instead of inventing matches.
- A PDF is read on the device: the browser extracts its text layer, plus approved exercise demonstration and guide links paired by the annotation layer or printed beside exercise names, and submits only those; no document bytes or page images reach the API or a model provider, and the links never enter a model request. A submitted link is re-validated server-side and kept only when it is an https URL on an approved demonstration or exercise-guide host; a YouTube link must name a video (never a channel page), and links are compared by the video and start time they play, not by share or feature parameters. Printed alternatives keep their printed wording unless the library spells the whole name, and are never renamed into the exercise they replace. The stored text is the whole source, is retained only while extraction is in flight, and is cleared at a terminal state. Pages without selectable text carry nothing and are reported, never guessed. A read stops only when its draft may not match the pages (weeks, days, sets or printed values missing, moved or unread); a document that contradicts itself (a note naming more sets than its table prints, a footer at odds with an instruction) is settled in review, and a note beside a table that states each set is only noted. What a model returns is reconciled, not refused: values are normalised into what a column holds and labelled inferred, and the outline's day count and duplicate-looking days are reported in review rather than failing a section. Complete clean pages are read locally even within mixed sections, with unresolved pages kept intact for model reads. Sections run concurrently and merge in outline order, committing an unbroken prefix. Completed responses and up to two metered targeted repairs resume after a restart; reads are reserved in one transaction, the longest sections start first, and rate-limited provider answers are retried with backoff. Week choices reconcile before gap checks, and selected branches receive final validation. Progress reports every section (queued, reading, checking, repairing, saved, committed) as tiles, eases its percentage between reports without passing the next milestone, shows elapsed time, and stays indeterminate during final verification.
- The Nutrition training-summary feed carries logged sessions plus, for a range that includes today, the active slot's unpassed training days this week as undated `upcoming` rows, read without creating progress rows.
- Nutrition owns weight/goal context; Workout owns sessions/progression/PRs. Integration data may inform Workout suggestions, but must never automatically change Nutrition calorie/macronutrient targets. Keep tokens scoped and optional-provider failures bounded and visible where actionable.
